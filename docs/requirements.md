# Requirements Document: Bluesky Feed Consumer

## Context

Build a proof-of-concept GCP service that consumes the Bluesky firehose in real-time, computes rolling summary statistics exposed via REST API and live-streamed to clients, and provides a "chat with AI persona" feature where users can have conversations with AI impersonations of selected Bluesky accounts. The service is consumed from new screens in an existing Bluesky app fork.

---

## A) Functional Requirements

### F1. Firehose Ingestion

- **F1.1** Consume the full Bluesky Jetstream firehose via persistent WebSocket connection
- **F1.2** Extract and classify events: posts, replies, likes, reposts
- **F1.3** For selected persona accounts: capture incoming posts/replies and append to their stored corpus in Postgres
- **F1.4** Graceful shutdown: flush in-memory stats to Postgres on SIGTERM to minimize data loss on deploy

### F2. Rolling Statistics

- **F2.1** Compute metrics in configurable time windows (defined in config file, e.g., 1, 5, 10 minutes)
- **F2.2** Core count metrics per window: post count, unique poster count, like count, repost count, reply count
- **F2.3** Period-over-period delta for each count metric: server computes `((current_completed_window / previous_completed_window) - 1)` and includes in API response
- **F2.4** Top-N lists per window (server maintains top 50): top liked posts, top reposted posts. Client shows 5 by default with "More" button to load 5 more per tap (up to 50 max)
- **F2.5** Language breakdown: track top L languages (L=20, configurable), group all others as "other". Use language tags from firehose metadata; untagged posts grouped as "other"
- **F2.6** Posting velocity: 2-second bucket timeseries over the last hour (1800 data points), streamed live to clients via SSE. Unified 2-second resolution — no separate granularity for chart vs. live value.
- **F2.7** Firehose consumer retains 1 hour of 2-second velocity buckets in memory (1800 integers, ~14KB)
- **F2.8** Snapshot completed windows to Postgres; accept loss of up to 1 window of in-flight data on deploy

### F3. Statistics API

- **F3.1** `GET /stats/{window}` — return count metrics and top-N for a configured window size
- **F3.2** Top-N limit parameter: client can request up to 50 items (server-maintained maximum)
- **F3.3** Live stats stream: SSE endpoint pushing updated stats to connected clients every 2 seconds (best-effort latency, target < few seconds from firehose event to client)
- **F3.4** Hard-coded facts and dimensions (no ad-hoc query support)

### F4. Persona Chat Feature

- **F4.1** `POST /personas` — register an account handle as a chat-able persona
- **F4.2** On registration: fetch up to 200 historical posts/replies via AT Protocol API, store in Postgres (limit configurable in config file)
- **F4.3** `GET /personas/{handle}/status` — returns readiness state (loading, ready, error) and metadata (post count, last_corpus_update timestamp)
- **F4.4** `POST /personas/{handle}/chat` — send a message, receive a streaming response (SSE) generated by Claude API using persona context
- **F4.5** Context injection strategy:
  - Always include: profile bio/description + pinned post (if any)
  - **Exclude** pure reposts (no persona voice). **Include** quote posts (persona's comment only, with brief reference to quoted post). **Include** posts with links. **Include** replies.
  - Adaptive post/reply ratio biased toward replies (reply_weight = min(natural_ratio + 0.2, 0.7))
  - Within each category: 60% most recent, 40% random sample from older posts
  - Floor: always include at least some replies if any exist
  - Include metadata per post: timestamp, post-vs-reply indicator, parent post text for replies
- **F4.6** Single persistent chat per persona: one conversation thread per registered persona, stored in Postgres
- **F4.7** `GET /personas/{handle}/chat` — retrieve conversation history for this persona
- **F4.8** `DELETE /personas/{handle}/chat` — clear entire conversation history for this persona
- **F4.9** Corpus refresh: as new posts arrive from firehose for selected personas, append to stored corpus
- **F4.10** Corpus freshness metadata: last_corpus_update timestamp available on status endpoint (displayed as debug info in client UI)
- **F4.11** Modular design: persona context provider as an interface, swappable to fine-tuned model in future

### F5. Bluesky App Integration

#### Navigation
- **F5.1** Stats and AI Chat accessed via hamburger flyout menu (not bottom tab bar). Bottom tab bar remains unchanged: Home, Explore, Chats, Notifications, Profile.
- **F5.2** Flyout menu additions: "AI Chat" item below "Chat"; "Stats" item below "Notifications"

#### Stats Dashboard
- **F5.3** Stats dashboard screen: live rolling stats with window tabs (1/5/10 min), period-over-period deltas (server-computed), velocity sparkline with live value, language breakdown, and top-N with segment control (Top Liked / Top Reposted)
- **F5.4** Top-N display: show 5 items by default, "More" button loads 5 more per tap (up to 50)
- **F5.5** Stats updated every 2 seconds via SSE; velocity sparkline and current value update in real time

#### Persona Chat
- **F5.6** Chat entry point: "Chat with AI {display_name}" in profile three-dot menu, positioned between "Add to lists" and "Go live" in the existing menu structure
- **F5.7** Chat inbox: accessible via hamburger flyout "AI Chat" item. Shows active persona chats with AI badge. Left swipe reveals red delete button (matching existing app Chats behavior).
- **F5.8** Chat screen: message thread UI following existing app conventions, with streaming response display and typing indicator
- **F5.9** Chat three-dot menu: only two items — "Go to profile" and "Leave conversation"
- **F5.10** Chat error handling: follow existing chat screen patterns for timeout/retry
- **F5.11** Persona readiness indicator: show loading state with progress (e.g., "142/200 posts") if persona history is still being fetched
- **F5.12** Debug info: corpus stats shown in small type on chat screen (post count, last updated, context posts selected)

#### General
- **F5.13** Follow all existing Bluesky app UI conventions (typography, spacing, theming, navigation patterns)

### F6. Operational Monitoring

- **F6.1** Dashboard showing: firehose connection status, events processed/sec, API request counts, error rates
- **F6.2** Use GCP Cloud Monitoring and Cloud Logging (built-in tools)

## B) Non-Functional / Technical Requirements

### NF1. Architecture & Code

- **NF1.1** Language: Python for all services
- **NF1.2** Module separation with clear boundaries:
  1. Ingestion module (firehose consumer, event parsing)
  2. Stats processing module (windowed aggregation, snapshots)
  3. Persona module (corpus management, context selection, chat generation)
  4. API module (REST endpoints, request handling)
- **NF1.3** Separation enables future rewrite of performance-critical modules (e.g., ingestion → Go)

### NF2. Deployment & Infrastructure

- **NF2.1** Single GCP Compute Engine instance (e2-small, 0.5 vCPU, 2GB RAM), ~$12/month. Runs firehose consumer, stats processing, REST API, and SSE endpoints in one process.
- **NF2.2** Database: Cloud SQL for PostgreSQL (db-f1-micro), ~$7/month
- **NF2.3** Total GCP budget: <= $100/month (estimated ~$25-30/month including Claude API usage)

### NF3. Storage

- **NF3.1** PostgreSQL as sole persistent store
- **NF3.2** Separate schemas: `stats` schema for rolling statistics, `chat` schema for personas and conversations
- **NF3.3** Rolling stats computed in-memory, snapshots written to Postgres at window boundaries (max 1 write/minute for shortest window)
- **NF3.4** Live stats served directly from in-memory state (single process, no DB round-trip for live data)

### NF4. Security & Auth

- **NF4.1** Simple static API key authentication (key in config, sent via header)
- **NF4.2** No rate limiting or abuse prevention required for demo
- **NF4.3** Anthropic API key stored as GCP Secret Manager secret (not in code/config)

### NF5. Performance & Reliability

- **NF5.1** Live stats latency: best-effort, target < few seconds from firehose event to client display
- **NF5.2** Chat response time: streaming, first token within ~1 second (bounded by Claude API)
- **NF5.3** Demo-grade reliability: brief outages acceptable, no HA requirements
- **NF5.4** Firehose reconnection: automatic retry with backoff on connection loss

### NF6. Observability

- **NF6.1** Structured logging to Cloud Logging
- **NF6.2** Custom metrics to Cloud Monitoring (events/sec, active connections, API latency)
- **NF6.3** Cloud Monitoring dashboard (no external tools like Grafana needed)

### NF7. Future Extensibility (architect for, don't implement)

- **NF7.1** RAG-based context selection for persona chat (currently recent + sampled)
- **NF7.2** Fine-tuned model backend for persona chat (swap out Claude API context injection)
- **NF7.3** Time-of-day aware persona responses (include timestamp metadata now; prompt engineering for temporal personality in future)

## Decisions Log

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Python for all modules | Best ML ecosystem; modular design allows future Go rewrite for perf-critical paths |
| 2 | Claude API + context injection (not fine-tuning) | Stays within $100/mo budget; higher quality conversation; architect interface for future swap |
| 3 | Single Compute Engine for everything | Simplest architecture: one process, shared memory for live stats. No two-URL client config. CE e2-small at ~$12/mo. Cloud Run dropped — no benefit for single-user demo. |
| 4 | Single chat per persona | Simpler UX (like DMs); single thread per persona |
| 5 | SSE for live stats | Push-based "live" feel; served directly from in-memory state |
| 6 | Bluesky language tags (no NLP) | Free, no processing cost; group untagged as "other"; YAGNI |
| 7 | 200 post history limit | ~10k words / ~13-15k tokens; fits Claude context window with room for conversation |
| 8 | Streaming chat responses | Near-zero added complexity with Claude SDK; better UX even for short responses |
| 9 | Exclude pure reposts from persona context | No persona voice in reposts; include quote posts (comment portion only) |
| 10 | Period-over-period deltas computed server-side | Client would need to wait up to 1 full window for data; server has previous window in Postgres |
| 11 | Stats/AI Chat in hamburger flyout, not tab bar | Match existing app navigation; don't modify the bottom tab bar |
| 12 | FastAPI + Pydantic Settings + SQLAlchemy/Alembic | Natural Python stack for async API + SSE + ORM |
| 13 | Claude Sonnet 4.6 for persona chat | Best quality/cost balance for conversational persona fidelity at demo scale |
| 14 | Adaptive response length | Match user message length — short question gets terse reply, longer gets more detail |
| 15 | 50 posts injected per prompt | ~6-7K tokens of context. Good persona coverage with room for conversation history |

## Notes on Live Stats Delivery

SSE (Server-Sent Events) chosen for live stats push. Key properties:
- HTTP/TCP-based persistent connection, server pushes events
- Auto-reconnect on interruption — client gets fresh data on reconnect (no stale backfill)
- React Native: supported via `react-native-sse` or `eventsource` polyfill
- Client should discard events with timestamps older than currently displayed (handles slow-network buffering)
- Fallback option: simple 2-second polling if SSE proves problematic in React Native (capture in tech spec as a decision point)
